Important migration findings

  1. Keep existing paths. WordPress uses /%postname%/. Blog articles currently live at the domain root; placing all articles under /blog/[slug] would change their URLs. Preserve root article slugs, existing nested archive paths, Arabic percent-encoded paths, trailing slashes, and query-based pagination where used. /blog/ remains the listing route.
  2. Retain redirects and deliberate removals. Both Rank Math and Redirection are active. Their database tables contain 32 configured 301 rules and 35 configured 410 rules. Live checks: {'matches status': 67}. One source contains an asterisk but is configured with exact matching; do not turn it into a wildcard that could block theme assets. Keep 410 responses for retired URLs instead of recreating removed content or forwarding every missing page to the homepage. Public noindex demo pages are a separate retention decision. Next.js defaults for permanent redirects use 308; use an explicit supported 301 strategy if preserving the existing code is required. A 410 needs an actual 410 response from the routing/hosting layer.
  3. Separate current language behavior from historical plugins. Fourteen published records have Arabic titles or slugs. The database retains 9,325 TranslatePress dictionary rows, but TranslatePress and GTranslate are absent from the active_plugins list. The legacy /arbic/ redirect leads to /arabic/, which currently returns 410. The live Arabic-slug homepage declares html lang=en-US, has no html dir value and no hreflang links. Preserve the real Arabic paths and content while deliberately correcting language semantics and destination links. Do not assume the historical translation tables define the live language switcher.
  4. Use the original design tokens. The active theme is softy-solutions-child over softy-solutions. Elementor uses Space Grotesk and Manrope; purple #6D2785, orange #FF4800, accent #FFFBBD, body #D2D2CF, background #020202 and surfaces #272727. The CSS has max-width:767px and max-width:1180px rules, and the kit enables a 1601px widescreen breakpoint. Match these explicitly in Tailwind rather than adopting default breakpoints.
  5. Resolve shared template dependencies. Header, footer, blog/archive, popup and search layouts live in database templates omitted by the Elementor ZIP. Use the extracted JSON, generated Elementor CSS, and screenshots as reference. Rebuild these as reusable React components; do not retain Elementor markup/plugins as the new runtime.
  6. Correct confirmed contact-link defects intentionally. The homepage includes a visible +92 number linking to a +47 tel: destination, and an info@nalksolutions.com label linking to softy-solutions@example.com. The mobile popup also contains theme example contact details. Contact-link evidence is exported separately; confirm intended destinations before implementation.
  7. Review existing redirect quality. The backed-up Google Ads service redirect points to social-media marketing. Some legacy patterns contain ellipses or invisible formatting characters. These are observed existing rules, not automatically valid migration decisions. The baseline records behavior so each change can be deliberate.
  8. Audit external design dependencies. The homepage requests a video from the theme demo host; Chromium recorded a cross-origin response block. Font and asset URLs may also be external. Recover the intended licensed media and font sources before making the new site independent of WordPress and the theme vendor.
  9. Preserve form behavior beyond appearance. The XML contains three Forminator forms and a quiz. Inventory which forms are live, their fields, validation, recipients, spam controls, consent, success/error states and delivery integration. Public snapshots cannot verify email delivery, private recipient configuration, or successful submissions.
  10. Use live SEO values as the baseline. 32 published records lack explicit Rank Math titles and 33 lack explicit descriptions in XML; global defaults may still produce live tags. Preserve actual final titles, canonicals, robots, social cards and schema, and separately review baseline defects rather than treating every missing explicit field as missing live SEO. The captured robots.txt has Disallow lines without a User-agent directive; generate a valid robots policy for the new site rather than copying it blindly.

What is still needed before launch

  • Demonstrate an isolated WordPress restore from the database and wp-content backup, using compatible WordPress/PHP versions. The supplied set does not demonstrate inclusion of wp-config.php, server-root .htaccess/web.config, hosting redirects, CDN rules, or server configuration.
  • Retain a private export of DNS, hosting/CDN redirects and cache rules, certificates/renewal arrangements, and email-related records. Check analytics/tag-manager IDs, Search Console verification, conversion events and consent settings. Website hosting changes must preserve mail routing.
  • Export Search Console page/query/indexing data, submitted sitemaps and important inbound links, and a longer analytics landing-page history. The Site Kit PDF is a short top-ten summary; zero key events are reported, so conversion tracking needs validation.
  • Complete an interaction review: desktop and mobile navigation, nested menus, language switcher, search, FAQs, sliders, sticky behavior, cookie/consent UI if present, and contact success/error states. Capture any important state absent from the representative screenshots.
  • Freeze content shortly before cutover, take a fresh database/uploads export, rerun the public capture into a new dated directory, import changes, and compare the final source baseline against staging. The current backup and live crawl are separate capture times.
  • Test rollback before cutover, keep the old hosting/backup available, and preserve deliberate 301/410 behavior. This review does not change DNS, WordPress, hosting, production redirects, or a Sanity dataset.

Recommended implementation

Build the public site in Next.js App Router with TypeScript strict mode and Tailwind. Use server-rendered content and reusable sections; keep client JavaScript limited to navigation, accordions, sliders, search and forms. Match the extracted spacing, fonts, colors, breakpoints and layouts before tuning performance. Marketing pages can live in typed code/data; Sanity should manage the blog as requested. A broad visual page builder is optional and is not required for this migration.

Model Sanity articles, authors, hierarchical categories/tags, reusable SEO fields and image metadata. Preserve a deterministic WordPress ID, immutable legacy path, slug, publication/modification dates, excerpt, author, featured image and inline media. Include language and translated-document references where justified by the real content. Convert article HTML to Portable Text with explicit support for tables, code, links, anchors, lists, embeds and image captions/alt text. Review conversion losses; sanitize any retained HTML and never execute imported scripts.

Import media first using a stable WordPress attachment-to-Sanity asset mapping, then taxonomy/authors, then articles. Make the importer idempotent and start with a dry-run manifest. Reconcile missing/duplicate assets and inspect representative English and Arabic articles before a full import. Import into a development dataset first.

Generate metadata on the server using the resolved baseline values, including canonical, language alternatives, social cards and robots. Preserve relevant Article/Service/Breadcrumb schema while removing plugin-specific duplication only after review. Generate a sitemap from intended canonical indexable routes. Preserve or map legacy /wp-content/uploads/... media URLs that are externally referenced. Treat staging indexing controls separately so noindex or blocked robots do not reach production.

Use Sanity draft preview, signed webhook verification and targeted cache revalidation. Keep write tokens and preview secrets server-side, with environment validation and least-privilege configuration. Implement real form delivery with server validation, spam protection and observable failure states. Optimize images without changing their visual crop or dimensions; use the matching fonts without layout shifts.

Validate every intended URL and every legacy rule, including 404/410 behavior; compare server HTML metadata, internal links, article formatting, schema and media; perform screenshot comparisons at the recorded viewports and at 767/768, 1180/1181 and 1600/1601 widths. Cover keyboard navigation, focus, reduced motion and RTL. Run type checks, lint/build checks, meaningful route/import/form tests, and field performance checks before DNS cutover.

The supplied Site Kit report shows 73.2% mobile visitors and mobile lab LCP of 4.9s versus desktop 1.1s. Prioritize the mobile hero, media, fonts and JavaScript while preserving the design. These are historical lab measurements, not a new performance test.

Implementation sequence: finish baseline and restore verification → route/content/asset mapping → shared design components → representative marketing and article templates → Sanity dry run and import → remaining routes and interactions → regression/SEO/performance review → content freeze/delta import → cutover and monitoring.
