Do not maintain conflicting completion claims in several places. The page matrix is generated from route records; it is not a second hand-edited acceptance database. Historical probe verification is distinct from the new implementation's test status.

The navigation scope register selects pages for further reconstruction; the route register
retains all historical routes and their existing implementation/acceptance records. Until
archive-only SEO dispositions are reviewed, an old `retain_page` plan is not authority to
expand the D-16 reconstruction scope or change runtime statuses. Do not rewrite historical
chunk counts. Regenerate the scope report from its identified capture and retain source hashes;
the [scope runbook](chunks/12-active-navigation-scope.md) records commands and limitations.

## Updating work

For each implementation change, update the affected route/decision/requirement and any changed command, contract or architecture choice. Evidence references must identify the build/content/environment and remain accessible. `accepted` requires evidence and a reviewer; `in_progress` does not mean visual parity has been established.

Keep observed source fields intact. Record target expectations separately. A new WordPress capture becomes a new baseline version with a source-difference review; do not silently replace the original observation.

The initial route register carries inferred family/locale hints. Inspect and correct planning fields as templates are measured. Do not mistake these hints for established reference measurements or a translation map.

## Documentation tooling

```powershell
.\.venv\Scripts\python.exe docs/tools/render_page_matrix.py
.\.venv\Scripts\python.exe docs/tools/check_docs.py
.\.venv\Scripts\python.exe docs/tools/check_docs.py --with-evidence
```

The renderer reads `registers/routes.json` and updates only `registers/page-matrix.md`. It does not mark work accepted. The default checker verifies internal links, register identities/counts, known status values and evidence requirements for accepted records, reporting unavailable external evidence links as deferred. `--with-evidence` also requires original external files, validates captured-file references and checks frozen source fingerprints. Use that mode locally or after CI retrieves the evidence. This is documentation consistency verification, not proof that a website test passed.

The existing archive/audit tooling is documented in [scripts/README.txt](../scripts/README.txt). Application command names listed elsewhere are planned until implemented; revise them to match actual package scripts in Phase 2 and test them from a clean checkout.

## Required implementation-era additions

Add concise, real guides when the corresponding capability exists: local setup/environment example, editor publishing/preview, importer/delta/recovery, test execution/baseline review, and the provider-specific release/rollback runbook. Link them from this index and remove superseded instructions in the same change. Do not create empty placeholder guides now.

Document nonobvious decisions, constraints and operational procedures. Comments should explain why a rule exists or a boundary matters; do not narrate obvious code or duplicate generated types.

## Review discipline

Check Markdown links and commands; ensure counts/status statements are current or explicitly historical; verify every acceptance claim has evidence; remove dead references and abandoned alternatives. Architectural changes update the ADR status and relevant design documents together. Keep a clean, navigable documentation set rather than a chronological transcript of experiments.
